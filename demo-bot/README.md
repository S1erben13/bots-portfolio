# QR-заявка для сервисной компании — демо-бот (Telegram + MAX)

Бот и веб-админка для фирм, которые обслуживают видеонаблюдение, домофоны, СКУД и шлагбаумы.

**Сценарий.** На оборудовании наклеен QR-код. Жилец или администратор объекта сканирует его, и открывается
бот в Telegram или MAX. Бот уже знает объект и оборудование, поэтому клиенту остаётся описать проблему и приложить фото.
Заявка получает номер, а клиент — уведомления при каждой смене статуса
(**новая → принята → техник выехал → выполнена**). Диспетчер получает новые заявки в мессенджере,
меняет статусы кнопками под уведомлением или в веб-админке.

```
 QR на камере ──► t.me/<бот>?start=NP2CAM ──► бот: «ЖК Северный парк, Камера у подъезда 1. Что случилось?»
                  max.ru/<бот>?start=NP2CAM        клиент: текст + фото ──► Заявка №00006
 Админка: статус «Техник выехал» ──► очередь уведомлений ──► бот: «Заявка №00006: техник выехал. Техник: Иванов С.»
```

## Что внутри

| Часть | Что делает |
|---|---|
| **Django 5.2 + PostgreSQL 16** | Модели: Компания → Объект → Оборудование (уникальный код для QR), Клиент (контакт в мессенджере), Заявка, История статусов, Фото, Очередь уведомлений |
| **Админка диспетчера** | Список заявок с цветными статусами и фильтрами. Массовые действия «Принять», «Техник выехал», «Выполнена». Фото и история статусов прямо в карточке заявки. Комментарий клиенту при смене статуса. Заявку можно завести вручную по звонку |
| **QR-наклейки** | PNG одной наклейки и PDF-лист A4 (сетка 3×3 с линиями реза) для всего объекта или для выбранного оборудования |
| **Страница `/q/<код>`** | Сюда ведёт QR: одна наклейка подходит и для Telegram, и для MAX, а клиент сам выбирает мессенджер |
| **Ядро без привязки к мессенджеру** | `service/services.py` (заявки, статусы) и `bots/engine.py` (сценарий диалога). Они получают на вход `IncomingEvent` и возвращают `Reply` |
| **Адаптеры** | `telegram.py` (aiogram 3), `max.py` (MAX Bot API через httpx), `console.py` (фейковый мессенджер для демо и тестов) |
| **Outbox** | Админка только ставит уведомление в очередь, а бот-процесс отправляет его с повторами и экспоненциальной паузой. Если Telegram или MAX недоступен, админка всё равно работает, а неотправленное видно в разделе «Уведомления клиентам» |
| **Тесты** | pytest: ядро, диалог, уведомления (повторы, порядок, аренда), адаптеры MAX/Telegram на подменённом HTTP, админка, наклейки, защита от «картинок» со скриптом |

```
demo-bot/
├── config/               настройки Django (всё из .env)
├── service/              домен: модели, services.py, admin.py, qr.py, страница QR
├── bots/
│   ├── engine.py         сценарий диалога (общий для всех мессенджеров)
│   ├── outbox.py         очередь уведомлений
│   ├── types.py          IncomingEvent / Reply / Button
│   └── adapters/         base.py, telegram.py, max.py, console.py
├── tests/
├── docs/examples/        пример наклейки PNG и листа PDF
└── docker-compose.yml    db + web + bot
```

Чтобы добавить новый мессенджер (например, VK), достаточно одного файла в `bots/adapters/` с методами `send()` и `poll_updates()`.

## Запуск (нужен только Docker)

```bash
cp .env.example .env
```

```bash
docker compose up -d --build
```

```bash
docker compose exec web python manage.py seed_demo
```

- Админка: http://localhost:8000/admin/ (логин и пароль `admin` / `admin` из `.env`, **поменяйте перед публикацией**)
- Страница QR: http://localhost:8000/q/NP2CAM/
- Демо-коды оборудования: `NP2CAM`, `NP2DMF`, `NP2BAR`, `BCACAM`, `BCASKD`, `BCANVR`

### Демо без токенов

Весь сценарий можно прогнать в терминале: клиент пишет боту, диспетчер меняет статусы, приходят уведомления.

```bash
docker compose exec web python manage.py simulate_chat --script
```

Интерактивный чат «от лица клиента» (`photo` — прислать тестовое фото, `skip` — «Без фото»):

```bash
docker compose exec web python manage.py simulate_chat
```

Заявки из симуляции сразу появляются в админке. Если сменить там статус, уведомление появится в логе бота:

```bash
docker compose logs -f bot
```

### Тесты

```bash
docker compose run --rm web pytest
```

## Подключение настоящих ботов

Токены вписываются только в `.env`. Этот файл не коммитится.

### Telegram
1. Откройте [@BotFather](https://t.me/BotFather), отправьте `/newbot`, задайте имя и username (должен оканчиваться на `bot`).
2. Скопируйте токен в `.env`: `TELEGRAM_BOT_TOKEN=...`, а username без @ — в `TELEGRAM_BOT_USERNAME=...`.
3. Выполните `docker compose up -d`. В логе бота (`docker compose logs bot`) появится строка `[telegram] бот @...`.
4. Проверка: откройте `https://t.me/<username>?start=NP2CAM`.

### MAX
1. Зарегистрируйтесь на [платформе MAX для партнёров](https://business.max.ru/self). Нужен профиль организации, ИП или самозанятого, и его должны верифицировать.
2. [Создайте бота](https://dev.max.ru/docs/chatbots/bots-create/create) и дождитесь модерации.
3. Токен находится в разделе «Чат-боты» → «⋮» → «Настройки» ([инструкция](https://dev.max.ru/docs/chatbots/bots-create/manage)). Впишите его в `MAX_BOT_TOKEN`, а короткое имя бота — в `MAX_BOT_NAME`.
4. Выполните `docker compose up -d`. Проверка: откройте `https://max.ru/<имя>?start=NP2CAM`.

### Куда ведёт QR
- `QR_TARGET=landing` (по умолчанию) — на `PUBLIC_BASE_URL/q/<код>/`, где клиент выбирает Telegram или MAX. Для этого сайт должен быть доступен из интернета: `PUBLIC_BASE_URL` — ваш домен, и его же надо добавить в `DJANGO_ALLOWED_HOSTS`.
- `QR_TARGET=telegram` или `max` — QR ведёт прямо в бота, публичный сайт не нужен.

Наклейки строятся в момент скачивания, поэтому после смены `PUBLIC_BASE_URL` или `QR_TARGET` их нужно скачать заново. Примеры в `docs/examples/` сделаны с адресом `localhost`, они только для показа.

## MAX: что сделано и что проверить на живом боте

Адаптер написан по официальной [OpenAPI-спецификации MAX Bot API](https://github.com/max-messenger/api-schema) (версия 0.0.34) и [документации dev.max.ru](https://dev.max.ru/docs-api):
домен `platform-api2.max.ru`, заголовок `Authorization: <токен>`, long polling `GET /updates` с `marker`,
deep link `https://max.ru/<бот>?start=<код>` → событие `bot_started` с полем `payload`, отправка `POST /messages?user_id=`,
кнопки `inline_keyboard` типа `callback`, ответ на нажатие `POST /answers?callback_id=`, входящие фото — вложение `image` с `payload.url`.

Без токена проверить на живом API не удалось. Ниже — что может отличаться от спецификации. Каждый такой пункт вынесен в константу в `bots/adapters/max.py`:
1. **Повторный переход по deep link.** Спецификация описывает `bot_started` как событие при нажатии «Начать». Неизвестно, придёт ли оно, если диалог с ботом уже открыт. Поэтому бот понимает и текст `/start <код>`, и код с наклейки, присланный обычным сообщением.
2. **Ответ на нажатие кнопки.** Нет данных, можно ли отвечать на `/answers` пустым телом, поэтому отправляется короткое уведомление `CALLBACK_ACK_TEXT = "Принято"`.
3. **Long polling.** Документация называет его «не для продакшена» и рекомендует webhook (`POST /subscriptions`), а для webhook нужен публичный HTTPS. Для демо оставлен polling. Переход на webhook — отдельная задача: нужен view, который передаёт тело запроса в `MaxAdapter.handle_update()`.
4. **Сертификат.** Документация просит добавить сертификат Минцифры в доверенные. В контейнере используется стандартный набор CA; если будут ошибки TLS, сертификат нужно добавить в образ.
5. **Длина deep link.** Payload — до 128 символов, а коды наклеек — 6 символов, так что лимит не мешает.

## Уведомления диспетчеру

1. В админке откройте «Диспетчеры» → «Добавить». Выберите компанию, мессенджер и Django-пользователя, от имени которого будут записываться смены статуса. Пользователь должен быть активен. ID диалога заполняется только ботом.
2. Сохраните запись: появится одноразовый код из 8 символов, действующий 24 часа. Откройте личный диалог с выбранным ботом и отправьте `/dispatcher КОД`. Код погасится после успешной привязки. Для повторной привязки выберите в списке админки действие «Выдать новый код привязки на 24 часа».
3. Новые заявки компании поступают всем активным привязанным диспетчерам через outbox с теми же повторами, арендой и порядком доставки. Карточка содержит объект, оборудование, описание (до 2200 символов; полный текст в админке), имя клиента, телефон при наличии, отметку о фото и ссылку на заявку. `PUBLIC_URL` задаёт публичный адрес админки; по умолчанию используется `PUBLIC_BASE_URL`.
4. Кнопки: у новой заявки — «Принять», у принятой — «Выехал» и «Выполнено», после выезда — «Выполнено». Нажатие обновляет исходное сообщение: статус, автор изменения и оставшиеся допустимые кнопки. Клиент получает обычное уведомление. Повтор старой кнопки обновляет карточку без повторной истории и уведомления. Чужая компания, неактивный диспетчер/пользователь и недопустимый переход получают ошибку.

Telegram, MAX и console поддерживают кнопки. В MAX карточка редактируется полем `message` в ответе `POST /answers` — по [официальной документации](https://dev.max.ru/docs-api/methods/POST/answers); на ошибку отправляется только `notification`. Проверки адаптеров выполняются без сети; работа с настоящими токенами требует отдельной проверки.

`seed_demo` создаёт консольного демо-диспетчера и выводит код привязки (при повторном запуске сохраняет действующий код). `simulate_chat --script` привязывает его, показывает карточку новой заявки и нажатие «Принять», затем уведомления клиенту. Для Telegram/MAX создайте отдельные записи диспетчеров с нужным мессенджером.

## Ограничения демо (осознанно)

- Один бот-процесс на мессенджер. В очереди уведомлений есть аренда (60 с) и сохраняется порядок отправки. Для нескольких параллельных воркеров нужен ещё токен владельца аренды. Доставка «как минимум один раз»: если процесс упадёт сразу после отправки, уведомление может прийти повторно.
- Фото клиентов перекодируются в JPEG (защита от SVG/HTML со скриптом). Фото, загруженные вручную через админку, проверяет только стандартное ImageField.
- Фото хранятся в docker-томе `media` и доступны только сотрудникам через Django. В проде их отдаёт nginx или S3.
- Многоарендность не сделана.
