# Заявки → CRM без потерь

Демо интеграции для портфолио: вебхуки Tilda, GetCourse и произвольных форм попадают в надёжную локальную очередь, затем в CRM. Поддерживаются amoCRM, Битрикс24 и локальная `fake` CRM без регистрации. Менеджер получает уведомление в Telegram; без токена результат записывается в лог.

```text
Tilda / GetCourse / Telegram / Salebot / форма
                     |
          POST /hooks/{source} + секрет
                     |
      нормализация + ключ идемпотентности
                     |
           SQLite: заявка и outbox
                     |
              фоновый воркер <----- /admin: повтор
                     |
         поиск контакта по телефону/email
                     |
       fake / amoCRM / Битрикс24 -> сделка
                     |
              Telegram или лог
```

## Запуск

Нужны Docker и Docker Compose. Все команды выполняются в `demo-crm/`.

```powershell
Copy-Item .env.example .env
# Измените HOOK_SECRET и пароль панели в .env.
docker compose up --build -d
docker compose exec app python demo_send.py
docker compose logs -f app
```

Панель: <http://localhost:8020/admin>. Имя пользователя и пароль задаются `ADMIN_USER` и `ADMIN_PASSWORD`. По умолчанию используется `CRM_PROVIDER=fake`: реальные аккаунты и токены для демо не нужны. SQLite хранится в Docker volume и переживает пересоздание контейнера; `docker compose down -v` удаляет данные.

`demo_send.py` отправляет пять запросов (JSON и form-urlencoded): четыре новых события и повтор первого. Две разные заявки одного человека должны создать один контакт и две сделки. Каждый запуск скрипта создаёт новые ключи событий. Для запуска скрипта внутри контейнера используется адрес `http://localhost:8000`; другой адрес задаётся `DEMO_URL`.

## Вебхуки

Доступны `POST /hooks/tilda`, `POST /hooks/getcourse`, `POST /hooks/generic`. Формат: `application/json` или `application/x-www-form-urlencoded`. Секрет передаётся заголовком `X-Hook-Secret` либо параметром URL `?secret=...`; заголовок предпочтительнее, поскольку URL может попасть в журналы прокси. Значение берётся из `HOOK_SECRET`.

Передавайте уникальный идентификатор события заголовком `Idempotency-Key`. Повтор события должен иметь тот же ключ. Для двух реальных обращений одного человека нужны разные ключи: дедупликация контактов и идемпотентность событий решают разные задачи. Без явного ключа применяется хеш нормализованной заявки; одинаковое содержимое будет считаться повтором.

```text
POST /hooks/generic
X-Hook-Secret: значение HOOK_SECRET
Idempotency-Key: order-123
Content-Type: application/json

{"name":"Иван","phone":"8 (999) 123-45-67","email":"ivan@example.test",
 "source":"telegram","utm_source":"portfolio","comment":"Консультация"}
```

Телефоны РФ приводятся к `+7XXXXXXXXXX`, email — к нижнему регистру. Сохраняются имя, источник, UTM и комментарий. В отправителе GetCourse/Salebot нужно настроить соответствующие поля и уникальный идентификатор события; вложенные специфичные структуры следует преобразовать в эту схему.

## Подключение amoCRM

В своём аккаунте создайте интеграцию и получите долгоживущий токен. Введите его самостоятельно в локальный `.env`, который исключён из Git:

```dotenv
CRM_PROVIDER=amo
AMO_BASE_URL=https://YOUR-SUBDOMAIN.amocrm.ru
AMO_TOKEN=YOUR-LONG-LIVED-TOKEN
```

Точное значение `CRM_PROVIDER` смотрите в `.env.example`. После изменения `.env` пересоздайте приложение: `docker compose up -d --force-recreate`. Адаптер ищет контакт по телефону/email, создаёт или связывает контакт со сделкой через API v4 `/api/v4/leads/complex` и добавляет примечание. Для полей UTM и дополнительных полей конкретного аккаунта при необходимости расширьте соответствие полей адаптера.

Документация: [контакты amoCRM](https://www.amocrm.ru/developers/content/crm_platform/contacts-api), [сделки amoCRM](https://www.amocrm.ru/developers/content/crm_platform/leads-api), [примечания](https://www.amocrm.ru/developers/content/crm_platform/events-and-notes).

## Подключение Битрикс24

В своём портале создайте входящий вебхук с правом CRM. Самостоятельно укажите полный URL с токеном:

```dotenv
CRM_PROVIDER=bitrix
BITRIX_WEBHOOK_URL=https://YOUR-PORTAL.bitrix24.ru/rest/USER_ID/WEBHOOK_TOKEN/
```

Адаптер использует `crm.duplicate.findbycomm`, `crm.contact.add` и `crm.deal.add`. У существующего контакта создаётся новая сделка. Секретная часть URL не должна попадать в Git или публичные логи. Поля обязательные именно для вашего портала, воронку и ответственного можно добавить в адаптер перед внедрением.

Документация: [поиск дублей](https://apidocs.bitrix24.ru/api-reference/crm/duplicates/crm-duplicate-find-by-comm.html), [создание контакта](https://apidocs.bitrix24.ru/api-reference/crm/contacts/crm-contact-add.html), [создание сделки](https://apidocs.bitrix24.ru/api-reference/crm/deals/crm-deal-add.html).

## Telegram

Владелец создаёт бота через BotFather и указывает `TELEGRAM_TOKEN` и `TELEGRAM_CHAT_ID` в `.env`. Затем нужно начать диалог с ботом или добавить его в нужный чат и пересоздать приложение. Без токена внешних сообщений нет. Не используйте реальные персональные данные для публичного демо.

## Надёжность и границы демо

HTTP-ответ об успешном приёме выдаётся после записи в SQLite. Воркер повторяет временные ошибки с экспоненциальной задержкой. Прогресс доставки сохраняется, поэтому ошибка уведомления не должна повторно создавать уже подтверждённую сделку. Ошибки и статус видны в `/admin`; ручной повтор возобновляет обработку сохранённой заявки.

Гарантия exactly-once для внешних CRM отсутствует: если CRM создала объект, но ответ потерялся или процесс завершился до сохранения идентификатора, повтор может создать дубль. Локальный ключ защищает от повторного приёма вебхука, но не закрывает это окно внешнего API. Перед промышленным внедрением нужен внешний идентификатор события в CRM с проверкой перед повторным созданием и процедура сверки неоднозначных запросов. Одновременные обращения одного контакта из других систем также могут создавать гонки дедупликации.

Запускайте один экземпляр приложения с одним воркером. Для работы с реальными заявками настройте HTTPS, надёжные секреты, резервное копирование SQLite, мониторинг очереди и срок хранения персональных данных. Не публикуйте SQLite и `.env`. Демо не заменяет настройку конкретного CRM-портала и проверку на его тестовых данных.

## Проверка

```powershell
docker compose run --rm app pytest -q
```

Тесты используют временную SQLite и HTTP-моки, реальные CRM и Telegram не вызываются. Проверяются нормализация, ключи идемпотентности, дедупликация, повторы, адаптеры и уведомления. В среде разработки с закрытым Docker socket тесты нужно запускать на машине с доступным Docker; успешный результат без фактического запуска не заявляется.
