# Демо: магазин цифровых товаров

Python 3.12, aiogram 3, FastAPI, SQLite, Docker Compose. Структура и оформление админки следуют `../demo-booking`. По умолчанию используется `fake`: деньги не списываются, для консольного прогона ключи и Telegram не нужны. Все файлы в `demo-files/` — явно подписанные заглушки. Настоящий `products/cctv-kit` сюда не включён.

## Быстрый запуск

Из `demo-shop/` в PowerShell:

```powershell
Copy-Item .env.example .env
```

Самостоятельно задайте `ADMIN_PASSWORD` в `.env`, затем:

```powershell
docker compose up --build -d
docker compose logs -f shop
```

Админка: http://localhost:8040/admin, логин `ADMIN_USER` (по умолчанию `admin`). Проверка HTTP: http://localhost:8040/health. Без `BOT_TOKEN` работает веб-часть; для бота заказчик сам вводит токен BotFather в `.env`. Затем `docker compose up -d --force-recreate`.

Порт опубликован только на `127.0.0.1:8040`. Для внешнего доступа нужны домен, HTTPS и обратный прокси. Укажите внешний HTTPS-адрес в `PUBLIC_URL`: он попадает в резервную ссылку на файл. Не записывайте пути `/d/*` в access log прокси: токен является секретом. Встроенный access log отключён.

Симулятор и проверки без Telegram и без запросов во внешнюю сеть:

```powershell
docker compose run --rm shop python -m shop.simulate --auto
docker compose run --rm shop python -m pytest -q
docker compose run --rm shop python -c "import ast,pathlib; [ast.parse(p.read_text(encoding='utf-8')) for d in ('shop','tests') for p in pathlib.Path(d).glob('*.py')]; print('Syntax OK')"
```

Симулятор использует временную БД, настоящий HTTP-маршрут скачивания через ASGITransport и записывающий отправитель вместо Telegram. Проверяет каталог → заказ → fake-оплату → одну выдачу при двух уведомлениях → пять скачиваний и отказ на шестом. Тесты ЮKassa используют `httpx.MockTransport`; тесты Telegram подают Update в Dispatcher без Telegram API.

## Сценарии

- `/start`: каталог, карточка, «Купить», email, оплата. `/start` также сбрасывает ввод email.
- `PAYMENT_PROVIDER=fake`: «Оплатить (тест)», мгновенное подтверждение без списания.
- `PAYMENT_PROVIDER=telegram`: `send_invoice` в RUB с токеном провайдера, проверка покупателя, статуса, суммы и валюты в `pre_checkout_query`, обработка `successful_payment`.
- `PAYMENT_PROVIDER=yookassa`: создание платежа API, постоянный для заказа Idempotence-Key, redirect-ссылка. Уведомление по `POST /hooks/yookassa` проверяется отдельным GET к API, затем сравниваются сохранённый payment_id, сумма и RUB. Тело webhook не считается доказательством оплаты.
- `/orders`: только оплаченные заказы текущего покупателя, возможность повторно получить файл. Администратор может повторить выдачу в `/admin`.

Заказ хранит снимок названия, цены и имени файла: изменение каталога не меняет уже созданный заказ. Статусы: `new → pending → paid → delivered`; неоплаченный заказ можно отменить через сервисный метод `cancel`. Ошибка отправки оставляет статус `paid`, повторная выдача доступна в `/orders` и админке.

После оплаты отправляется один `send_document` с резервной ссылкой в подписи. Каждый новый токен создаётся `secrets.token_urlsafe(32)`, действует 72 часа и допускает до 5 запросов скачивания. Это персональная непредсказуемая ссылка с ограниченным использованием, а не буквально одно скачивание: численный лимит выбран по ТЗ. Ссылку может использовать любой, кто её знает; отдельного входа покупателя на сайте нет. При повторной выдаче создаётся новая ссылка, прежняя действует до своего срока/лимита. Неуспешная передача HTTP-файла тоже может потратить попытку.

## Подключение ЮKassa заказчиком

**Ограничение для цифрового каталога:** Telegram требует Telegram Stars (`XTR`) для продажи цифровых товаров и услуг внутри Telegram. Поэтому рублёвый Telegram Payments и redirect ЮKassa здесь реализованы как запрошенные демонстрационные адаптеры, а не готовая схема запуска продажи этих файлов внутри Telegram. Для такого запуска нужна отдельная реализация Stars; для самостоятельного внешнего магазина требуется отдельный пользовательский сценарий. Не включайте реальные платежи этого цифрового каталога через RUB в Telegram. Источник: [Telegram — цифровые товары и Stars](https://core.telegram.org/bots/payments-stars).

Для проверки интеграции ЮKassa:

1. Заказчик самостоятельно регистрирует/подключает магазин, проверяет применимость к своему статусу и включает тестовый режим в кабинете. Вносит тестовые `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` в `.env`; приложение не определяет, тестовый это магазин или боевой.
2. Для API-адаптера выбирает `PAYMENT_PROVIDER=yookassa`, задаёт `PAYMENT_RETURN_URL` (страница возврата покупателя) и `PUBLIC_URL`. Страница возврата не подтверждает оплату.
3. Настраивает HTTPS-webhook `https://ваш-домен/hooks/yookassa` для `payment.succeeded`. Внешняя сеть нужна только для реальной интеграции. GET-проверка обязательна даже при ограничении источников webhook.
4. Для отдельного ознакомления с Telegram Payments: BotFather → нужный бот → Payments → ЮKassa, тестовый токен в `PAYMENT_PROVIDER_TOKEN`, `PAYMENT_PROVIDER=telegram`. Применять только с учётом ограничения цифровых товаров выше.
5. Сам проверяет тестовый платёж, повторное уведомление, отправку файла и чек. Переход на реальные ключи выполняет только после проверки применимости платёжного сценария и фискализации.

API использует HTTP Basic Auth магазина, `POST /v3/payments`, заголовок `Idempotence-Key` и `GET /v3/payments/{id}`. Ошибка сети при создании допускает повтор того же заказа с тем же ключом в сервисе. Автоматического фонового опроса незавершённых оплат нет.

Официальные источники: [формат API и идемпотентность](https://yookassa.ru/developers/using-api/interaction-format), [справочник](https://yookassa.ru/developers/api), [webhook и проверка подлинности](https://yookassa.ru/developers/using-api/webhooks). Ограничение IP на прокси можно добавить по актуальным диапазонам из последнего источника; диапазоны в проекте не захардкожены.

## Чеки

Бот запрашивает и проверяет email перед оплатой. В API-платёж передаются `receipt.customer.email`, одна позиция, сумма в RUB, `quantity=1.00`, `payment_mode=full_payment`, `VAT_CODE` и `PAYMENT_SUBJECT` (`service` либо `commodity`). В Telegram invoice передаётся `provider_data.receipt`, также включена передача email провайдеру. Настройки НДС и предмета расчёта заказчик выбирает для своего товара и подключения; значение `VAT_CODE=1` в примере не является налоговой рекомендацией.

Самозанятый оформляет чек в «Мой налог» либо использует интеграцию ЮKassa с «Мой налог» — **проверить в кабинете ЮKassa**. Передача `receipt` сама по себе не подтверждает, что фискализация подключена или чек сформирован. Доступность и настройки интеграции проверяет заказчик. Формат receipt: [чеки при платежах — документация ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/payments).

## Администрирование и файлы

`/admin/catalog`: добавление и редактирование товаров, цена в копейках, описание, имя файла и активность 0/1. Удаление заменяется архивированием. Имя файла задаётся относительно `FILES_ROOT` (`/app/files` в Docker). Разрешены только существующие файлы внутри корня после разрешения пути и символических ссылок. Файлы не загружаются через админку: положите их в `demo-files/` или замените read-only bind mount в Compose и обновите товар. Не подменяйте демозаглушку незаметно для покупателя.

`/admin`: фильтр заказов по статусу, выручка по `paid_at` за даты включительно в UTC, ручная выдача. Период относится к показателю выручки; список заказов фильтруется отдельно по статусу. `/admin/export?status=delivered`: CSV с копейками и epoch-временем UTC, без email и токенов. Опасные начала названий экранируются для Excel.

Basic Auth обязателен, пустой пароль отключает доступ; формы защищены CSRF-токеном процесса. Прямой запуск `python -m shop` без пароля запрещён. Не публикуйте Basic Auth без HTTPS. Секреты только в `.env`; он исключён из Git и Docker build context. Email хранится в SQLite для чека, но не выводится в журналы/админку/CSV. Ограничьте доступ к Docker volume и резервным копиям; срок хранения персональных данных определяет владелец магазина.

`seed_demo` автоматически и идемпотентно добавляет отсутствующие товары при запуске, не перезаписывает правки. Можно вызвать отдельно: `docker compose run --rm shop python -m shop.seed_demo`.

## Границы демо

- Только один процесс/worker приложения и одна локальная БД. Внутри процесса выдача сериализована async-lock, отправка и отметка `delivered_at` выполняются в SQLite-транзакции. Параллельные повторы уведомления не создают вторую выдачу.
- Атомарной транзакции между Telegram и SQLite нет. Если Telegram принял документ, а процесс упал до коммита, повторная обработка может отправить документ ещё раз. При неоднозначном сетевом таймауте также возможен дубль. Гарантия exactly-once при таких сбоях не заявляется. Длительная отправка удерживает write-lock БД.
- FSM ввода email в памяти: перезапуск сбрасывает незавершённый ввод. Повторную оплату зависшего заказа из интерфейса и автоматическую сверку не добавляли. Успешно оплаченный заказ сохраняется независимо от доставки.
- При ошибке уведомления администратору подтверждение завершится ошибкой; повтор webhook повторит уведомление без новой выдачи файла. Для Telegram без повторного события администратор проверяет заказы в веб-панели. Фоновой очереди уведомлений нет.
- Возвраты, чеки возврата, изменение статуса при отмене со стороны провайдера, лимиты покупок, антиспам, миграции БД и работа нескольких реплик в демо не реализованы. Telegram-бот требует личного диалога с покупателем, а для уведомлений — доступного `ADMIN_CHAT_ID`.
